# md-peruse 概略要件定義書

## 1. 文書の目的

本書は、閲覧専用Markdownビューワー `md-peruse` のプロダクト要件、主要な機能要件、非機能要件、技術構成および配布方針を定義する。

詳細な設計判断と未決事項は [design-decisions.md](./design-decisions.md)、実装順序と品質ゲートは [dev-flow.md](./dev-flow.md) に記載する。画面構成の参考資料は [uimock.html](./uimock.html) とし、UIモック自体は要件を定義しない。

`uimock.html` は初期段階の視覚参考であり、次の点は本書と一致しない。参照時はモック内の記述ではなく本書を優先する。

- モック内のサンプルMarkdown本文が旧構成（`marked.js`、`pulldown-cmark`）を記述しているが、採用するのはunified（remark + rehype）である。
- モックはCDNから `marked.js` を読み込むが、製品ではCDNを使用せず依存を同梱する。
- モックはHTMLでメニューバーを描画しているが、メニューの実装方式は未決である。

## 2. プロダクト概要

| 項目 | 内容 |
| --- | --- |
| プロダクト名 | md-peruse |
| 目的 | AI駆動開発で更新される設計書、仕様書、タスクリストの観測とレビューに特化した、軽量で応答性の高い閲覧専用Markdownビューワーを提供する |
| コアバリュー | 完全Read-only、アイドル時の低負荷、高速な起動、MermaidやGFMなどのリッチ表現の確実な可視化 |
| 対象プラットフォーム | Windows 11（x64、ARM64） |

編集機能、常駐プロセス、バックグラウンドインデックスは実装対象外とする。

## 3. ターゲットユースケース

### 3.1 AIエージェントによる文書更新の観測

ターミナルなどで動作するAIエージェントが更新したMarkdown文書をサブ画面に表示し、ファイル変更に追従して自動的に再描画する。

エージェントは一時ファイルへ書き出してからrenameする置換（atomic replace）を行うことが多く、短時間に連続した書込みが発生する。この書込みパターンで表示が壊れないことを要件とする。

### 3.2 アーキテクチャと状態遷移の視覚検証

AIが生成したMermaidのシーケンス図、クラス図、フローチャートなどを描画し、論理破綻や依存関係の矛盾を目視で確認できるようにする。

### 3.3 人間によるレビューとGO判定

仕様のブレやエッジケースを、ファイルを誤って変更するリスクなく確認し、実装またはリリースへ進むかを判断できるようにする。

## 4. 機能要件

### 4.1 ワークスペースとナビゲーション

| 要件 | 内容 |
| --- | --- |
| フォルダー選択 | ネイティブダイアログから閲覧対象のルートフォルダーを選択できる |
| フォルダー走査 | ルート直下を最初に取得し、サブフォルダーは展開時にRust側で遅延取得する |
| ノイズ除外 | バージョン管理メタデータ、依存関係ディレクトリ、ビルド成果物ディレクトリ、隠し項目、システム項目、reparse pointを除外する。除外名の一覧は [design-decisions.md](./design-decisions.md) を正本とする |
| ツリー表示 | 左ペインに展開可能なフォルダーツリーを表示する |
| ツリーの表示対象 | フォルダーと `.md`、`.markdown` を表示する。それ以外のファイルを表示するかは未決とする |
| キーボード操作 | 上下キーで移動、左右キーで展開と折りたたみ、`Enter` で選択、`Home` と `End` で先頭と末尾へ移動できる |
| パンくずリスト | 現在表示しているファイルの階層パスをタイトルバー直下に表示する。上位セグメントを選択すると、対応するフォルダーをツリー上で展開して選択状態にする。ルートより上へは移動できない |
| ペイン幅調整 | 左ペインとプレビュー領域の境界を、マウスドラッグとキーボードの両方で変更できる |
| タブ | 複数のMarkdownを切り替え、同一文書の重複タブを作らず表示できる |
| 対象ファイル | `.md` と `.markdown` を開ける |
| ワークスペースを閉じる | Watcherを停止し、タブと探索キャッシュを破棄して未選択状態へ戻す |

### 4.2 Markdownプレビュー

| 要件 | 内容 |
| --- | --- |
| Read-only | 本文の編集を禁止し、テキストの選択とコピーだけを許可する |
| GFM | テーブル、タスクリスト、取り消し線、引用、コードブロックを表示する |
| Mermaid | `mermaid` コードブロックを検出し、非同期でSVGへ変換する。構文エラー時はエラー内容を安全に表示する |
| シンタックスハイライト | 明示された言語のコードブロックをハイライト表示する。言語の自動判定は行わない |
| 数式 | `$...$` と `$$...$$` の数式をKaTeXで描画する。数式を含む文書を開いたときだけKaTeXを読み込む |
| 見出しアンカー | 見出しへ安定したIDを付与し、同一文書内の `#anchor` リンクで移動できる |
| 相対画像 | `./assets/image.png` などの相対パスを現在のMarkdownファイル基準で解決し、ワークスペース内の許可画像だけを表示する |
| ホットリロード | 開いているファイル、およびワークスペースルート以下の変更をRust側で検知し、アクティブ文書のプレビューを自動更新する |
| 入力上限 | Markdown、画像、Mermaidに上限を設ける。上限値は「9. 制約と上限」に示す |
| 部分的失敗の分離 | 画像、Mermaid、ハイライトの個別の失敗が本文全体の描画を壊さない |

YAML front matterの扱い、および文書内検索は未決とする。

### 4.3 表示とアプリケーション制御

| 分類 | 操作 |
| --- | --- |
| ファイル | フォルダーを開く、ワークスペースを閉じる、アプリを終了する |
| タブ | 次のタブ、前のタブ、タブを閉じる |
| 表示 | サイドバー表示切り替え、文字サイズ変更、文字サイズのリセット、強制再読み込み |
| テーマ | ダーク、ライト、OS設定への追従 |

メニューをネイティブメニューとして実装するかWebView内で実装するかは未決とする。

### 4.4 起動とOS連携

| 要件 | 内容 |
| --- | --- |
| 単一インスタンス | 原則として1インスタンス、1ウィンドウで動作する |
| ファイル関連付け | MSIX manifestで `.md` と `.markdown` の関連付けを宣言する。既定アプリにするかはWindowsのユーザー設定に委ねる |
| 関連付け起動 | 起動済みインスタンスがある場合は引数を既存インスタンスへ渡し、既存ウィンドウを前面化する |
| WebView2欠落時 | WebView2 Runtimeの欠落や初期化失敗を、ネイティブ側で原因と公式の修復先とともに表示する |

### 4.5 初期版へ含めるか検討中の機能

- 最近使ったフォルダーと最後のワークスペース復元
- 単一Markdownまたは単一フォルダーのドラッグ＆ドロップ
- ワークスペース外の相対Markdownリンクをloose tabで開く動作
- 文書内検索（`Ctrl+F`）
- リンク遷移とアンカー遷移に対する戻る／進む操作
- YAML front matterのメタ情報表示
- 非Markdownファイルのツリー表示
- 英語UIの併記

判断は [design-decisions.md](./design-decisions.md) の未決事項で管理する。

## 5. 非機能要件

### 5.1 パフォーマンス

以下は暫定目標であり、x64実機、SSD、ウイルス対策既定設定、MSIXインストール済みの条件で測定する。実測に基づく確定はPhase 1で行う。

| 指標 | 暫定目標 |
| --- | --- |
| コールドスタート | ウィンドウ表示まで2秒以内、操作受付まで3秒以内 |
| ウォームスタート | 操作受付まで1秒以内 |
| 文書切り替え | 1 MiB、Mermaidなしの文書で、選択から描画完了まで500 ms以内 |
| 変更反映 | debounce待ちを除き、変更検知から再描画完了まで500 ms以内 |
| ツリー展開 | 1000項目のディレクトリ展開を300 ms以内 |

ファイル変更時に必要な範囲だけを再読込し、不要な再走査を避ける。

### 5.2 リソース効率

- アプリ終了後に常駐プロセスを残さない。子プロセスとして起動されるWebView2プロセスも終了させる。
- バックグラウンドインデックスを作成しない。
- ファイル変更検知以外の定期的なディスクI/Oを行わない。
- メモリ目標はWebView2のホストプロセスを含めて定義する。アイドル時（1文書表示、Mermaidなし）のprivate working setは、全プロセス合計で300 MB以内、Rust側プロセス単体で50 MB以内を暫定目標とする。

WebView2を採用する構成では、アプリプロセス単体が数十MBに収まってもプロセス群の合計はそれを大きく超える。「数十MB」という表現は測定対象が曖昧なため、上記のとおり測定単位を定義して置き換える。

### 5.3 アクセシビリティ

- ツリー、タブ、メニュー、パンくずリスト、ペイン境界をキーボードで操作できるようにする。
- 適切なセマンティクスとARIA属性を設定する。
- OSのハイコントラスト、`forced-colors`、`prefers-reduced-motion` に対応する。
- `forced-colors` 有効時も、Mermaid図とコードブロックの内容が判別できる表示にする。

### 5.4 セキュリティ

想定する脅威は、信頼できないMarkdown、画像、SVG、Mermaid定義をローカルで開くことである。攻撃者はファイル内容を制御できるが、ローカルでのコード実行権限は持たないことを前提とする。

- Raw HTMLとMarkdown内JavaScriptを実行せず、ソースとして表示する。
- 解析結果をstrict allowlistでsanitizeし、sanitize済みの構造だけを描画する。
- `javascript:`、`data:`、`file:`、任意の `ms-` schemeを遮断する。
- リモート画像とワークスペース外の画像を初期版では遮断する。許可するUIは初期版に含めない。
- Frontendへネイティブ絶対パスや汎用ファイルシステム権限を渡さない。
- 外部script、任意通信、iframe、objectをCSPで遮断する。

### 5.5 プライバシーとテレメトリ

- アプリからのネットワーク通信を行わない。例外は、ユーザーが明示的に外部リンクを開いたときにOS既定ブラウザーへ委譲する場合だけとする。
- 使用状況テレメトリとクラッシュレポートの外部送信を行わない。
- Microsoft Storeの提出時に、データ収集を行わない旨を申告し、対応するプライバシーポリシーを提示する。

### 5.6 国際化

- 初期版のUI言語は日本語とする。
- UI文字列はコードへ直接埋め込まず、後から言語を追加できる形で分離する。
- 英語UIを初期版へ含めるかは未決とする。

### 5.7 サードパーティライセンス

- 同梱するOSS依存関係のライセンス表記を、アプリ内から参照できるようにする。
- ライセンス一覧はCIで依存関係から生成し、手動更新に依存しない。
- Microsoft Storeの提出物にライセンス表記の欠落がないことを確認する。

## 6. 技術スタック

| レイヤー | 採用技術 | 主な責務 |
| --- | --- | --- |
| デスクトップシェル | Tauri v2 | ウィンドウ管理、WebView2ホスト、権限制御、FrontendとRust間のIPC |
| Backend | Rust | フォルダー走査、ファイル読込、ファイル監視、パス検証 |
| Frontend | React + TypeScript + Vite | 画面構成、状態表示、Markdownプレビュー、ユーザー操作 |
| パッケージ管理・スクリプト実行 | Bun | JavaScript依存関係、Frontendの開発・ビルド・テストコマンド |
| テスト | `bun:test` | Frontendの単体テストとコンポーネントテスト |
| コード品質 | Biome、`tsc --noEmit`、Lefthook | Lint、Formatting、型検査、Git Hooks |
| Markdown | unified（`remark-parse`、`remark-gfm`、`remark-rehype`、`rehype-sanitize`、`rehype-react`） | GFMを含むMarkdownの構文解析、Raw HTML無効化、AST段階のsanitize、React要素への変換 |
| リッチ表示 | Mermaid、`lowlight`（`highlight.js/core`）、KaTeX | 図、許可言語のコードブロック、数式を遅延描画 |
| SVG sanitize | DOMPurify | Mermaid生成SVGのsanitize |
| Windowsパッケージ | MSIX、winapp CLI | Package Identity、パッケージ生成、開発用署名、Store提出 |

### 6.1 アーキテクチャ

```text
+---------------------------------------------------------------+
|                    Frontend（WebView2）                       |
|  React + TypeScript + Vite                                   |
|  - Titlebar / Breadcrumb / TreeView / Resizer / Preview      |
+---------------------------------------------------------------+
                              ▲ │
                    Tauri IPC │ │ invoke / event
                              │ ▼
+---------------------------------------------------------------+
|                    Backend（Rust / Tauri v2）                 |
|  - フォルダー走査                                             |
|  - ファイル読込                                               |
|  - ファイル変更監視                                           |
|  - ローカル画像のパス検証とcustom protocol配信                |
+---------------------------------------------------------------+
```

Frontendからローカルファイルシステムへ直接アクセスさせず、ファイル操作はTauri commandへ集約する。ユーザー画像は検証済みresource IDを使う専用custom protocolから提供し、ワークスペース全体をasset protocolへ公開しない。

## 7. パッケージングと配布

### 7.1 配布方針

| 項目 | 方針 |
| --- | --- |
| パッケージ形式 | MSIX |
| 配信先 | Microsoft Store |
| 対応アーキテクチャ | x64、ARM64 |
| 製品署名 | Microsoft Storeによる署名を利用する |
| 開発用署名 | ローカルインストールとWACK検証に限り自己署名証明書を使用する |
| 更新 | Tauri Updaterを導入せず、Microsoft Storeの更新機構へ一本化する |

### 7.2 バージョニング

- 製品バージョンはSemVerの `MAJOR.MINOR.PATCH` とし、Gitタグ `vMAJOR.MINOR.PATCH` を正本とする。
- MSIXのPackage Versionは `MAJOR.MINOR.PATCH.0` とする。第4要素はStoreが予約するため常に0とする。
- Storeへ提出するたびにバージョンを単調増加させる。
- `Package.appxmanifest`、`tauri.conf.json`、`Cargo.toml`、`package.json` のバージョンをCIで同期し、不一致をビルド失敗として扱う。
- x64版とARM64版は同一バージョンで生成する。

### 7.3 ビルドと提出の流れ

```text
Tauriでx64 / ARM64をビルド
    ↓
実行ファイルとFrontendリソースをステージング
    ↓
winapp CLIでアーキテクチャ別MSIXを生成
    ↓
ローカルインストールとWACKで検証
    ↓
Partner Centerへ提出
    ↓
Microsoft Storeが署名、配信、更新
```

Tauri CLIはMSIXを直接生成しないため、MSIX生成を独立したパッケージング工程として扱う。winapp CLIはPublic Previewであるためバージョンを固定し、`Package.appxmanifest` とパッケージ用アセットをツールから独立して管理する。

## 8. CI/CD方針

- GitHub ActionsでFrontendとRustの品質チェック、テスト、Releaseビルドを実行する。
- Windows上でx64とARM64の成果物を個別に生成する。ARM64はネイティブARM64ランナーの利用可否を確認し、利用できない場合はクロスコンパイルとする。
- winapp CLIでMSIXを生成し、生成物をCI artifactとして保存する。
- WACKをStore提出前の品質ゲートとする。
- テストカバレッジをCodecovで可視化する。
- 依存関係とGitHub ActionsをRenovateで更新する。
- Partner Centerへの初回登録と初回審査申請は手動で行う。
- 更新版のStore Submission API連携を自動化する。ただし、API実行前に手動承認ゲートを設ける。

## 9. 制約と上限

上限値の根拠、および暫定と確定の区別は [design-decisions.md](./design-decisions.md) を正本とする。

| 対象 | 上限 | 状態 |
| --- | --- | --- |
| Markdownファイルサイズ | 10 MiB | 確定 |
| 対応文字コード | UTF-8（BOM有無）、BOM付きUTF-16 LE／BE | 確定 |
| 画像1件のファイルサイズ | 32 MiB | 確定 |
| 画像の同時読込 | 2件 | 確定 |
| 画像のピクセル寸法 | 未決 | 未決 |
| Mermaid 1図の入力サイズと描画時間 | 未決 | 未決 |
| KaTeXのマクロ展開と出力サイズ | 未決 | 未決 |
| 同時に開けるタブ数 | 未決 | 未決 |
