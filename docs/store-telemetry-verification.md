## 2. Usageレポートを確認する

1. Partner Centerで `md-peruse`（Store ID `9P35BW61FN4W`）のUsageレポートを開く。カスタムイベントを表示できるか、権限や画面上の警告も確認する。
2. 初回公開版を含む期間を選び、開始・終了日、画面のタイムゾーン（表示がなければ「未表示」）、データの最終更新時刻を記録する。観測日時はUTCとする。
3. Custom eventsとCustom events breakdownで、5種類のイベント名と件数を記録する。表示がないイベントは「未表示」とし、画面が明示した0件と区別する。
4. Package versionの選択肢と表記を保存し、0.1.0.0と0.1.1.0をそれぞれ選ぶ。カスタムイベントの表・グラフにも適用されるか確認する。標準UsageのApp Version Breakdownを見ただけで、カスタムイベントも分離できたと判定しない。分離できなければ、その制約を記録する。
5. Market、Device type、OS versionなど他のフィルターも揃える。内訳が複数行になる場合は、同じ期間・版・フィルター内でイベントごとに合計する。内訳と総計を重複して加算しない。
6. 同じ条件で標準Sessionsの件数も記録する。カスタムの `session_start` との差は観測記録にとどめ、標準Sessionsを分母にした率や、両者の対応付けを作らない。
7. エクスポートできれば表・グラフを保存し、できなければ表示値とフィルターを転記する。公開リポジトリには集計値・確認条件・資料の参照だけを残し、アカウント情報、テナント情報、認証情報、一時URLを含む画面や原本は入れない。

根拠: Microsoftの [Usage report](https://learn.microsoft.com/en-us/windows/apps/publish/analyze-app-performance/usage-report) は、カスタムイベントの発生件数とpackage versionを含む内訳を説明している。[Log custom events for Partner Center](https://learn.microsoft.com/en-us/windows/uwp/monetize/log-custom-events-for-dev-center) はStore公開を確認の前提としている（2026-10-08確認）。

## 3. イベントを発生させて反映を追う

現在のStore版で不足するイベントを確認するときの手順。実際の本番集計へ入るため、必要最小限の起動にとどめ、自然利用の件数と混ざることを記録する。過去版の実績を現在の版で代用しない。

1. 起動前に、Store配布のパッケージバージョンと `SignatureKind: Store` を確認する。開発用MSIXでは送らない設計である。Windowsの版と診断データの現在の設定を記録する。設定は確認のために勝手に変更しない。
2. 実行前のUsageレポートを2章の条件で保存する。
3. アプリが終了している状態から、専用の小さなMarkdownを関連付けで開き、本文の表示完了を確認する。これは `session_start`、`launch_by_association`、`open_md_ok` の発火条件を満たす。
4. 利用者の操作で検証用フォルダーを開く。起動時の前回フォルダーの復元は `open_folder` の対象外である。
5. 検証用の不正なUTF-8などを持つMarkdownを開き、文書全体の失敗表示を確認する。Mermaidや数式だけの失敗は `open_md_fail` の対象外である。既存の利用文書は変更しない。
6. 起動中に2つ目のMarkdownを関連付けから開き、既存ウィンドウのタブで表示されることを確認する。この経路は新しいセッションや関連付け起動イベントを増やさない。1プロセス内で各イベントの発火は最大1回である。
7. 操作日時（UTC）と表示結果を記録し、通常終了する。アプリは送信結果をログへ残さないため、操作成功をSDKの送信成功やレポートへの反映と同一視しない。
8. 同じ期間・版・フィルターでレポートを再確認し、未反映だった最後の確認時刻と、初めて反映を観測した時刻を保存する。欠けているイベントも名前ごとに記録する。

**反映遅延に固定の待ち時間を置かない。** 集計の増分は他の利用者の操作も含み、送信欠落もありうる。集計だけで自分の操作に帰属できなければ、操作から観測までの時間は参考値として記録し、正確な遅延やSLAを確定しない。未表示だけで送信失敗とも断定しない。過去の発生時刻が残っていないイベントから、初回公開時の正確な遅延を復元しない。

## 4. 母集団と診断データ設定の関係

標準Usage指標とSDKのカスタムイベントは別々に確認する。Windowsのクラッシュ診断の収集条件をSDKイベントへ当てはめない。

- 画面の説明・情報アイコンとMicrosoftの現行資料に、収集対象や診断データ設定の条件があるか確認し、URL、確認日、対象の指標を残す。
- 検証用端末の設定と操作・観測の結果を記録しても、集計値から特定端末を識別できない。別の設定の端末と件数を比べるだけでは、オプトイン端末だけが対象であることや、両指標が同じ母集団であることは証明できない。
- 判断できない場合は、OS・SDK・パッケージの版と観測条件を整理し、Microsoftへ確認するための質問を用意する。「標準Usageと `StoreServicesCustomEventLogger.Log()` の各収集条件」「任意の診断データが無効な端末の扱い」「両指標の母集団の一致」を分ける。問い合わせの送信は別途行う。
- 裏付けが得られるまでは母集団を「未確認」とし、オプトイン端末に限ることや「同じ母集団だから率は正しい」と断定しない。件数から全利用者、インストール数、DAUへ外挿しない。確認できた制約は、反映遅延と並べてdesign-decisions.md 11.4へ反映する。
