## 起動とメモリ

小さな検証ワークスペースを復元する条件で測定した。WebView2のリモートデバッグを有効にし、CDPで文書の選択と本文表示を確認した。「文書を開けるまで」はCDP接続・測定処理・文書読込を含む上限側の値であり、操作受付時間そのものを厳密に測った値ではない。

| 指標 | 5回の中央値 | spec.mdの目標 |
| --- | --- | --- |
| 再起動後の初回起動：ウィンドウ表示 | 172.8458 ms | 2,000 ms以内 |
| 再起動後の初回起動：文書を開けるまで | 657 ms | 操作受付3,000 ms以内 |
| ウォーム：文書を開けるまで | 593 ms | 操作受付1,000 ms以内 |
| Rust単体のPrivate Working Set | 4.76 MB | 50 MB以内 |
| 子WebView2を含むPrivate Working Set | 92.00 MB | 300 MB以内 |

コールド5回のウィンドウ表示は172.8458 / 202.8614 / 171.1004 / 168.0476 / 174.9458 ms、文書表示は664 / 852 / 652 / 644 / 657 msだった。各回でWindowsを再起動し、異なるOS起動日時を確認した。OSの先読みなどは無効化していないため、完全なキャッシュ除去は主張しない。

メモリは文書1件、Mermaidなし、1秒間隔で5回測定した。MBは1,000,000 bytes。Private BytesではなくPrivate Working Setを使い、本体から子孫プロセスをたどって合計した。通常終了後、対象の7プロセスがすべて終了した。

### 測定用クリックの失敗と切り分け

初期のウォーム測定では入力失敗が2回あった。追加診断で、行がDOMに存在しフォーカスもあるが、初回描画フレーム前に送ったCDP入力のmousedown / mouseup / clickがDOMへ1件も届かない失敗を再現した。起動済み画面への実クリックでは文書を開けた。

ツリーの表示後にrequestAnimationFrameを2回待ち、座標を取り直して1回だけクリックを送る比較では、5回すべて入力3イベントと文書表示を確認した。文書表示までの値は593 / 609 / 641 / 578 / 568 ms、中央値593 msだった。再現した失敗は、DOMの存在だけで入力受付の準備完了を判断した測定方法の問題と結論づけた。WebView2内部の配送機構や、当時の記録がない過去2回との同一原因までは直接証明していない。アプリのコードは変更していない。

| 確認項目 | 実機結果 |
